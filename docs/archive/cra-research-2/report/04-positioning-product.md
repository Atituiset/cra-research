# 04 · 产品定位 / 形态 / 信息架构 / User Journey

> 对应 mvp.md §十八 #5/#6/#17。定位从 03 的能力空位推出，形态与 IA 按产品级模型设计，5 个 User Journey 覆盖主干业务。

## 1. 定位选项分析（三个候选，选一个主战场）

| 选项 | 一句话 | 优势 | 风险/反证 | 评估 |
|---|---|---|---|---|
| A. **合规工具（GRC for CRA）** | 义务清单→证据收集→文档生成 | 2026-2027 紧迫感直接变现；采购语言与法务对齐 | GRC 巨头（OneTrust 等）可加模板 [基于公开资料]；**纯文档生成可被审计师否掉**（没有真实扫描/判定数据的合规是空壳）| 窄楔子，不做主定位 |
| B. **又一个 SCA 扫描器** | 更准的 Component→CVE | 买家认知成本低 | 07 章：扫描层严重同质化；NVD 降级反而利好**有自建情报的大厂**；新进入者无数据规模优势 | ❌ 放弃 |
| C. **CRA-native Product Security 平台（漏洞生命周期 + 证据）** | 产品级模型上跑"发现→判定→修复→报告→留证"闭环，VEX 与事件报告为尖刀 | 直接命中 03 §4 的 4 个低竞争空位；数据模型不背历史包袱（03 §5）；义务表(02 §6)整个成为需求池 | 需要触达"产品安全"决策者（非纯采购）；Reachability/Agent 需自建或集成 | ✅ **主定位** |

### 1.1 定位陈述（Positioning Statement，供路演/官网）
> **对欧盟及全球的"含数字元素"产品制造商的产品安全与合规团队**：
> 你们被要求在 24 小时内判定漏洞影响、为每个结论提供可审计证据、维护 5 年支持期与 10 年记录（CRA Art.14 / Annex I）；
> 传统 SCA 只给你一张更长的告警清单。
> **本平台是 CRA-native 的漏洞生命周期系统**：以产品×版本为主实体，把 SBOM、多源情报、可达性证据收敛为**带理由的 VEX 判定**，自动装配事件报告与监管应答——
> **不是更多告警，而是每个结论都带证据。**（与通用扫描器的区别：判定工作流+证据图+产品级模型；与 GRC 的区别：判定来自真实分析引擎而非问卷。）

### 1.2 差异化支柱（= 03 章 4 个空位，按防守难度排序）
1. **证据图（Evidence Graph）**——最深护城河：判定→证据→快照→10 年，数据随时间复利。
2. **VEX 判定工作流**——市场传导最刚需：客户交货要的就是这个文件，而竞品多数只做"导出"。
3. **事件报告状态机（24h/72h）**——法规已生效的尖刀功能，演示冲击力最强。
4. **Reachability**——必须有（否则判定没原料），但**单独不构成差异化**（Endor/Semgrep/Snyk/Oligo 已 ship）→ 定位为"判定引擎的一环"，不作为品牌主词。

## 2. 产品形态（Form Factor）

- **默认形态：B2B SaaS 多租户**（欧盟数据驻留选项后置到 P1，但架构上 Day 1 分离"数据域"）。
  - 买家是产品安全/合规团队（5-30 人），不是个人开发者 → **团队协作/审批/审计是底色**。
- **接入面**（按优先级）：
  1. **CI 门禁**（GitHub/GitLab webhook：PR 扫描、发布门禁）——现有 SCA 的入口心智。
  2. **SBOM 上传/定期摄取**（SPDX/CDX 文件、container registry hook）——CRA 采购的第一入口。
  3. **代码托管集成**（仓库只读 + agent 草稿 PR，06 章）。
  4. **API/CSV 导出**（VEX/CSAF/事件报告）——第一天就要有，下游客户在等文件。
  5. **IDE/CLI**：P2（本产品主用户不在编辑器里做判定）。
- **非目标形态（明确不做）**：端点 EDR、网络 IDS、通用 GRC、漏洞赏金平台——见 09 Q5 边界。

## 3. 信息架构（IA）——侧边栏即业务流程

> IA 直接编码 03 §4 的六域；一级导航 ≤7 项，顺序 = 用户心智的时间序（先有产品，再有判定，最后报告）。

```
侧边栏（一级）
├── 1. 产品（Products）              ← 产品级模型的一等公民
│     ├── 产品目录 / 版本 / 支持期台账
│     └── 组件清单（来自 SBOM/扫描，组件级引用挂此）
├── 2. 漏洞（Vulnerabilities）       ← 多源归一后的漏洞主视图
│     ├── 告警流（按产品×版本过滤）
│     └── 关联详情（区间来源/置信度/别名——五层透明化）
├── 3. 判定（Assessments）           ← 本产品的差异化中心
│     ├── Reachability 结果（call path 证据）
│     ├── Exploitability 研判面板
│     └── VEX 工作台（状态机×证据挂载×SLA 升级）
├── 4. 修复（Remediation）
│     ├── 建议（升级/backport/缓解/配置）
│     ├── Agent 修复会话（草稿 PR，06）
│     └── 验证（复扫/复核状态）
├── 5. 报告（Reporting）             ← CRA 收口
│     ├── 事件报告（24h/72h 时间线）
│     ├── SBOM 与 VEX/CSAF 发布
│     └── 合规中心（义务→证据完备度看板）
├── 6. 证据（Evidence）              ← 10 年留痕，图谱+时间线双视图
└── 7. 设置（Settings）              ← 数据源、策略、团队、集成
```
- **详情页模式**：任何实体（产品/漏洞/判定/事件）统一四段式：**概览 → 关联 → 证据时间线 → 行动**。
- **跨实体跳转纪律**：告警→判定→修复→报告必须 1 次点击可达（"证据可回溯"的 UX 化）。

## 4. 五个 User Journey（对应典型任务，含入口→判定→出口）

### J1 · 新产品上线合规体检（Week-1 onboarding，最高频的"激活时刻"）
- **入口**：上传 SBOM（或连 GitHub/registry 自动拉）。
- **流程**：SBOM 解析→组件质量评分→多源关联→告警产生→批量初步判定（reachability 未跑时默认 `under_investigation`+置信度）→生成"合规缺口清单"（缺支持期声明/缺流程文档/未定义报告联系人）。
- **出口**：产品页出现"支持期未声明"等 3 项待办 + 初始 SBOM 版本 1 + 可分享的合规进度只读链接。
- **价值时刻**：5 分钟内让用户看到"离 Annex I 差 3 件事"，而不是一堆 CVE。

### J2 · 每周漏洞研判（批量 VEX 判定，效率主场景）
- **入口**：告警流筛选"新情报命中产品 A"（KEV 标红置顶）。
- **流程**：逐条进入判定面板：情报源对比→reachability 结果（有则展示 call path，无则一键跑）→EPSS/KEV/暴露面证据卡→选状态（affected/not_affected/fixed/investigating）→系统要求填写 justification（受控词表）→自动挂证据快照→批量应用到同根因告警。
- **出口**：VEX 草稿列表 + 判定 SLA 倒计时（investigating 超 72h 自动升级到负责人）。
- **价值时刻**：一次判定 30 秒内完成且**无法不留证据**（UI 强制）——与"导出型"竞品的分水岭。

### J3 · 事件响应：某漏洞 24h 报告（法规尖刀场景，demo 首选）
- **入口**：KEV 新增命中 / 用户手动标记"疑似在野利用"→自动创建事件。
- **流程**：事件时间线状态机启动（T0 记录）→系统汇聚：受影响产品快照（冻结当前 SBOM+版本）、严重度判定辅助、缓解措施、是否恶意→24h 预警草稿预填（SRP 字段结构）→人工审批→提交标记→72h 正式通知草稿（根因/利用方式/影响/受影响清单）→纠正措施后 ≤14d final 草稿→所有动作进证据图。
- **出口**：三份带时间戳的报告草稿 + 提交状态 + 冻结的产品快照 ID。
- **价值时刻**：倒计时看板上"距 24h 截止还剩 06:12"，全部字段已预填——**这是竞品演示里最缺的画面**。

### J4 · 修复与验证闭环（工程主场景）
- **入口**：判定=affected 且优先级达标 → 进入修复。
- **流程**：建议四选（升级/backport/配置缓解/暂无法修复+VEX 理由）→接受"升级"→agent 起草 PR（06 章架构：修改+测试+证据附言）→CI 复扫+复核 reachability→状态迁移 `fixed`→自动更新 VEX（fix version）→通告下游草稿。
- **出口**：merged PR + VEX=fixed + 验证记录挂证据。
- **价值时刻**：PR 描述里自带"本 PR 消除 CVE-X（证据：升级前后 SBOM diff + 复扫结果）"。

### J5 · 交付前客户应答（销售/客户成功场景，付费意愿来源）
- **入口**：客户问卷/邮件："请提供产品 B v3.2 的 SBOM、CVE 列表、VEX、支持期声明"。
- **流程**：一键"生成客户应答包"→系统按版本冻结数据→装配 SBOM(SPDX+CDX)+当前 affected 漏洞表+对应 VEX+支持期+DoC 草稿→（可选）证据附录（审计方可核对的判定链）→水印/有效期。
- **出口**：zip/门户链接，生成记录入证据图。
- **价值时刻**：过去 2 天的手工拼表 → 2 分钟，且客户可点进证据链接验证（信任感）。
